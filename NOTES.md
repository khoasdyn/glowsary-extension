# Notes and open mismatches

This file is the running log of mismatches and open gaps across the project: between the UI and the design, between Figma and the code tokens, between a request and PRD.md, between PRD.md and DESIGN.md, and anything else that does not line up yet. Claude records items here so nothing is lost while a decision is pending. Each item stays until it is resolved, then it is marked done or removed.

How to read an item: the area it touches, what the mismatch or gap is, and its status. Open means it still needs a decision or a fix. Resolved means it is settled.

47. The in-page Save form does not load the project fonts, so the "Add Word" title is not in Copse. Root cause confirmed 2026-06-09: the in-page form is drawn by a content script, and its CSS (content.css) loads the font files with a URL that contains the i18n placeholder `__MSG_@@extension_id__`. Chrome does not replace that placeholder in content-script CSS (it only works in regular extension pages), so the font URL stays broken, the Copse and Poppins files never load on the page, and text falls back to the system sans-serif. The serif "Add Word" title is where this is most visible; Poppins also fails to load but is harder to notice because the fallback is also sans-serif. On the options page the same fonts load fine because that page uses plain relative font URLs that resolve against the extension origin. The font files are already listed in web_accessible_resources, so the fix is to load them with a URL that resolves at runtime in the page context (the extension's own resource URL), not the i18n placeholder. Fonts needed: Copse Regular and Poppins Regular, Medium, and SemiBold, all already declared. Follow-up 2026-06-09: Codex applied the runtime FontFace fix and it is still wrong, but the earlier CSP guess was wrong too. On GitHub the in-page hover popup renders the saved word in Copse correctly, which proves the Copse font does load on the page, so CSP is not blocking it. Real root cause confirmed by reading the code: a font-name mismatch combined with CSS custom-property indirection. The shared token file (tokens/typography-tokens.js) sets the primitives at :root to the bare names `--font-family-heading: "Copse"` and `--font-family-body: "Poppins"`. The semantic text-style tokens (semantic-typography-tokens.js) declare at :root `--text-style-section-title-font-family: var(--font-family-heading)`, so that token's value is computed at :root and resolves to the bare "Copse". On the management page this works because options.css registers the @font-face under the bare names "Copse" and "Poppins", so the loaded name matches the token. In the in-page form, content.js registers the fonts under the prefixed names "Glowsary Copse" and "Glowsary Poppins" (to avoid clashing with a host page's own fonts), and content.css overrides `--font-family-heading`/`--font-family-body` to those prefixed names only on `.glowsary-popup` and `.glowsary-dialog`. Elements that reference `--font-family-heading` directly (the popup word, the field labels) get the prefixed, loaded name and render in Copse/Poppins. The dialog title reaches the font through the semantic token instead, which was computed at :root where `--font-family-heading` is still the bare "Copse" (the local `.glowsary-dialog` override does not reach a token already computed at :root). The bare "Copse" is not the name the in-page font was loaded under, so the title falls back to the system sans-serif. The field inputs hit the same path but the miss is invisible because Poppins falls back to another sans-serif. Fix: make the names line up in the in-page context, so the name the fonts are registered under matches the name the :root font-family primitives resolve to. Two coherent options: (A) register the in-page fonts under the bare names "Copse"/"Poppins" and drop the "Glowsary " prefix in content.css (simple, but risks clashing with a host page font of the same name); or (B) keep the prefixed names and set the in-page :root values of `--font-family-heading`/`--font-family-body` to the prefixed names too, so the semantic tokens resolve to a loaded font (preserves the namespacing). Area: UI consistency, design tokens, font naming. Status: open; build fix needed.
